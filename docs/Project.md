# 《孤岛温差》开发手册

## 1. 项目概述

### 1.1 项目名称

**孤岛温差**

### 1.2 项目定位

《孤岛温差》是一款基于地图的匿名情绪记录与情绪热力可视化软件。

用户可以在城市或校园中的某个地点匿名留下自己的情绪、温度值和一句话故事。系统会将这些情绪数据聚合成一张“温差地图”，让用户看到不同地点所承载的孤独、压力、焦虑、治愈、安心与共鸣。

它不是传统社交软件，也不是普通地图软件，而是一款融合了**匿名情绪表达、地图交互、数据可视化、轻度共鸣互动和智能体陪伴**的城市 / 校园情绪感知平台。

### 1.3 一句话介绍

《孤岛温差》是一款匿名情绪地图应用，用户可以把自己在某个地点产生的情绪以“温度”的形式留在地图上，系统将这些情绪聚合成城市或校园的温差地图，让人们看见孤独、压力、治愈与共鸣在空间中的分布。

### 1.4 项目核心关键词

匿名、情绪地图、温差、校园、城市、孤独感、共鸣、热力图、智能体聊天、NLP 情感分析、PaddleNLP、模型训练、GaussDB、数据可视化、隐私保护。

## 2. 产品理念

### 2.1 核心概念

“孤岛”代表个体在城市或校园生活中的情绪孤独感。

“温差”代表不同地点、不同时间、不同人群之间的情绪差异。

在这款软件中，情绪不再只是文字，而是一种可以被记录、聚合、分析和看见的空间信号。

例如：

* 图书馆：压力 -6℃
* 操场：治愈 +4℃
* 宿舍区：疲惫 -3℃
* 湖边草坪：安心 +5℃
* 校门口：离别 -5℃
* 地铁站：焦虑 -4℃

用户在地图上看到的不是普通地点，而是一个个被情绪赋予温度的空间。

### 2.2 产品核心价值

#### 对用户的价值

1. **匿名表达情绪**
   用户可以在不暴露身份的情况下留下自己的感受。

2. **获得情绪共鸣**
   用户可以看到同一地点也有人有过类似情绪，从而减轻“只有我这样”的孤独感。

3. **发现情绪区域**
   用户可以通过地图看到哪里压力较高，哪里更温暖、更适合独处和放松。

4. **获得智能陪伴**
   用户可以和智能体聊天，让智能体帮助自己整理情绪、生成留言、推荐情绪标签和温度。

5. **形成城市 / 校园情绪画像**
   系统通过统计报告展示某个区域在不同时间段的情绪变化。

#### 对课程项目的价值

1. 主题新颖，不是传统管理系统。
2. 具有地图交互、数据可视化、匿名社区、智能体聊天、后台管理等多个技术点。
3. UI 可以做得很有氛围感。
4. Demo 展示效果强，适合软件工程课程答辩。
5. MVP 范围可控，后续扩展空间大。

## 3. 目标用户与使用场景

### 3.1 目标用户

主要面向城市和校园中的年轻人，尤其是：

* 大学生
* 研究生
* 初入职场青年
* 独居青年
* 通勤族
* 情绪表达需求较强但不愿公开社交的人

### 3.2 用户痛点

1. 有情绪但不想发朋友圈。
2. 想表达，但不想被熟人看见。
3. 想知道是否有人在同一个地方有过类似感受。
4. 想找到城市或校园里让人放松、安全、有归属感的地点。
5. 情绪很乱，说不清楚自己到底怎么了。
6. 不想打扰别人，但希望有人能接住自己的情绪。

### 3.3 典型用户画像

#### 用户 A：备考大学生

* 年龄：20 岁
* 场景：考试周长期待在图书馆
* 痛点：压力很大，但不想向熟人倾诉
* 使用方式：在图书馆留下“焦虑 -7℃”，看到很多人也在这里感到压力

#### 用户 B：独居上班族

* 年龄：25 岁
* 场景：晚上下班经过地铁站
* 痛点：疲惫、孤独、缺少表达出口
* 使用方式：在地铁站投递一句话，看到附近有人留下“今天也辛苦了”

#### 用户 C：城市漫游者

* 年龄：22 岁
* 场景：喜欢散步、探索城市
* 痛点：想找到有故事、有情绪温度的地点
* 使用方式：查看城市温差地图，寻找治愈地点和情绪故事

#### 用户 D：情绪表达困难者

* 年龄：21 岁
* 场景：情绪低落，但不知道怎么描述
* 痛点：想表达，却不知道该写什么
* 使用方式：先和智能体“岛屿回声”聊天，再由智能体帮忙整理成情绪标签、温度和一句话留言

## 5. 核心功能设计

## 5.1 用户与匿名身份模块

### 功能说明

用户可以选择匿名使用，也可以在后续版本中注册账号保存自己的情绪记录。

MVP 阶段建议不做复杂账号系统，只做匿名身份。

用户第一次进入系统时，后端生成一个匿名用户 ID，前端存储在本地。

匿名身份不能只依赖 userId。MVP 阶段需要同时生成 anonymousId 和 anonymousToken，后端通过 token 校验该匿名用户是否有权限删除自己的留言、提交反馈或查看自己的历史投递。

### 功能点

1. 匿名进入
2. 生成匿名用户标识
3. 生成匿名访问 token
4. 保存用户投递记录
5. 支持删除自己的留言
6. 支持查看自己的历史投递
7. 后续可扩展登录功能

### 匿名身份示例

用户不显示真实昵称，而显示：

* 漂流者 1027
* 夜行岛民
* 温差记录者
* 匿名岛屿
* 湖边来信人
* 深夜路过者

### 实现方式

前端首次进入时检查本地是否存在 anonymousId。

如果不存在，则调用后端接口：

```text
POST /api/users/anonymous
```

后端返回：

```json
{
  "anonymousId": "island_8f3a29",
  "anonymousToken": "anon_token_7db9f3c2",
  "nickname": "匿名岛民1027"
}
```

前端将 anonymousId、anonymousToken 和 nickname 保存到 localStorage 中。

后续需要用户身份的接口，不直接相信前端传入的 userId，而是通过请求头传递匿名 token：

```text
Authorization: Anonymous anon_token_7db9f3c2
```

后端根据 token 找到用户，再执行发布、删除、互动和反馈等操作。

| 温度范围       | 情绪状态           | 颜色      |

| +7℃ 到 +10℃ | 高温，快乐、幸福、希望    | 金色 / 暖红 |

### 情绪类型建议

* 焦虑

* 疲惫
* 失落

* 迷茫
* 压抑

#### 正向情绪

* 治愈
* 安心
* 快乐
* 怀念
* 平静
* 希望
* 归属感
* 被支持

### 情绪温度设计

温度范围建议为：

```text
-10℃ 到 +10℃
```

| 温度   | 含义         |
| ---- | ---------- |
| -10℃ | 极度崩溃、强烈痛苦  |
| -7℃  | 明显孤独、焦虑、失落 |
| -4℃  | 疲惫、烦躁、空落   |

| +3℃  | 放松、稍微安心    |

| +10℃ | 强烈幸福、充满希望  |

```text

    ↓

    ↓

    ↓

    ↓
点击发布
    ↓
地图上出现新的情绪点
    ↓
系统提示：“你的温度已留在这座岛上。”
```

### 发布成功文案

可以随机显示：

1. 你的温度已经留在这座岛上。
2. 这座岛收到了一点你的温度。
3. 有些情绪被看见，就已经不再完全孤单。
4. 你留下的温度，会被后来的人轻轻看见。

## 5.4 情绪温差地图模块

### 功能说明

系统根据用户投递的数据，在地图上生成情绪热力图。

热力图用于展示某一区域整体偏冷还是偏暖，也可以展示某一种情绪的聚集程度。

### 热力图类型

1. 综合温差图
2. 孤独热力图
3. 焦虑热力图
4. 治愈热力图
5. 压力热力图
6. 安全感热力图
7. 深夜情绪图

### 综合温差算法简化版

```text
地点温度 = 附近所有情绪温度的平均值
```

### 改进版计算方式

```text
地点温度 = Σ(情绪温度 × 时间权重 × 距离权重) / Σ(时间权重 × 距离权重)
```

其中：

1. 距离越近，权重越高。
2. 时间越近，权重越高。
3. 过旧数据权重降低。

### 时间衰减建议

| 数据时间 | 权重  |
| ---- | --- |
| 当天   | 1.0 |
| 一周内  | 0.7 |
| 一个月内 | 0.4 |
| 一个月前 | 0.2 |

### 距离权重建议

| 距离           | 权重  |
| ------------ | --- |
| 0 - 100 米    | 1.0 |
| 100 - 300 米  | 0.8 |
| 300 - 500 米  | 0.6 |
| 500 - 1000 米 | 0.3 |

## 5.7 匿名故事墙模块

### 功能说明

用户可以浏览某个地点附近的匿名留言。

留言以卡片形式出现，不强调社交关系，只强调情绪共鸣。

### 设计原则

1. 不做强社交。
2. 不显示真实身份。
3. 不支持公开私信。
4. 不强调粉丝、关注、个人主页。
5. 重点是共鸣，而不是认识对方。

### 留言卡片内容

每条卡片包含：

1. 情绪标签
2. 温度
3. 时间
4. 地点
5. 一句话内容
6. 共鸣按钮
7. 举报按钮

### 卡片示例

```text
孤独  -6℃

“今晚从图书馆出来，突然觉得整座校园都很安静。”

23:41 · 图书馆附近

[我也有过] [抱抱] [点亮]
```

## 5.8 共鸣互动模块

### 功能说明

用户可以对他人的情绪留言做轻量反馈。

### 互动类型

不建议使用“点赞”，因为点赞会削弱情绪表达的认真感。

建议使用：

1. 我也有过
2. 抱抱
3. 点亮
4. 谢谢你说出来
5. 愿你暖一点

### 互动限制

1. 每个用户对同一条留言同一种互动只能点击一次。
2. 不开放评论区，避免争吵和攻击。
3. 不开放私信，避免骚扰。
4. 支持举报。
5. 可以取消自己的互动。

### 互动反馈文案

```text
有 12 个人也在这座岛上与你共鸣。
```

或：

```text
有人轻轻点亮了你的温度。
```

## 5.9 智能体聊天模块

### 功能定位

智能体聊天功能是《孤岛温差》的情绪陪伴模块。

用户可以在匿名状态下与智能体进行对话，表达自己的情绪、困惑或当下感受。智能体会根据用户输入内容、当前情绪温度、所在地点以及地点情绪数据，提供温和的回应、情绪梳理、留言生成和治愈地点推荐。

该功能不是心理诊断工具，也不是专业心理咨询服务，而是一个低压力、匿名、克制的情绪陪伴入口。

### 智能体名称

推荐名称：

**岛屿回声**

含义：用户说出的话会像回声一样被温柔接住，不被评价，不被打扰。

### 智能体可以做的事情

1. 倾听用户表达
2. 温和回应用户情绪
3. 帮助用户总结当前感受
4. 推荐情绪标签
5. 推荐温度值范围
6. 帮用户生成一句匿名留言
7. 引导用户发布匿名情绪
8. 推荐附近治愈地点
9. 解释某个地点的情绪状态
10. 在用户明显低落时给出求助建议

### 智能体不应该做的事情

1. 不做心理疾病诊断。
2. 不承诺解决用户问题。
3. 不评价用户情绪对错。
4. 不诱导用户泄露真实身份。
5. 不要求用户提供精确位置。
6. 不替代专业心理咨询。
7. 不自动将聊天内容发布到地图。

### 智能体典型场景

#### 场景一：用户不知道怎么写留言

用户输入：

```text
我也不知道怎么说，就是觉得很累。
```

智能体回复：

```text
听起来你不是简单的困，而是撑了很久之后的疲惫。

如果你愿意，可以把它留成：

情绪：疲惫
温度：-4℃
一句话：今天好像一直在努力，但还是觉得有点空。
```

按钮：

```text
[使用这条留言] [重新生成] [先不发布]
```

#### 场景二：用户想找一个温暖地点

用户输入：

```text
我不想待在教学楼了，附近有没有舒服一点的地方？
```

智能体回复：


### 6.4 推荐技术栈

#### 前端

确定方案：

1. Vue 3
2. Vite
3. TypeScript
4. Pinia
5. Vue Router
6. Naive UI
7. ECharts
8. 高德地图 JS API

#### 后端

确定方案：

1. Spring Boot：业务后端，负责用户、情绪、地图、互动、统计、后台管理等接口。
2. FastAPI：NLP 模型服务，负责 PaddleNLP 模型推理和训练结果加载。
3. HTTP / JSON：业务后端与 NLP 服务之间通过内部接口通信。

#### 数据库

确定方案：

```text
Huawei Cloud GaussDB / openGauss 兼容数据库
```

GaussDB 在本项目中不只是业务数据库，还承担以下职责：

1. 存储匿名用户、情绪投递、地点、互动、举报、聊天会话等业务数据。
2. 存储每日 / 每周温差统计快照。
3. 存储 NLP 模型训练样本、模型版本和预测记录。
4. 存储用户修正后的标签反馈，用于后续模型迭代。
5. 在支持向量类型或扩展能力的环境中，存储文本 embedding，用于相似情绪检索。

需要地理空间查询时，优先推荐：

```text
GaussDB / openGauss + GIS 扩展能力
```

课程项目简单版可以先不强依赖复杂 GIS 扩展，而是使用：

```text
latitude + longitude + location_grid
```

附近查询可以先用经纬度范围筛选，再在后端计算距离。这样更容易保证 Demo 可运行。

#### NLP 与模型训练

确定方案：

1. PaddleNLP
2. ERNIE / BERT 中文文本分类模型
3. FastAPI 模型服务
4. GaussDB 存储训练样本、预测结果和模型版本

MVP 阶段可以先使用 PaddleNLP Taskflow 或规则模型完成情感分析；正式训练阶段再使用自建校园情绪数据集微调中文预训练模型。

#### 缓存

暂缓：

```text
Redis
```

MVP 阶段可以不引入 Redis，直接从 GaussDB 查询。后续如果热力图和报告接口压力较大，再引入 Redis。

后续用途：

1. 缓存热力图数据
2. 缓存热门地点
3. 缓存日报统计
4. 缓存智能体会话上下文

## 10. 数据库设计

本项目数据库统一采用 GaussDB。MVP 阶段可以使用普通关系表完成业务闭环；如果部署环境支持 GIS 或向量扩展能力，可以进一步支持空间索引和相似情绪检索。

设计原则：

1. 业务数据、统计数据和模型训练数据统一沉淀在 GaussDB 中。
2. 不保存用户原始精准坐标，只保存模糊化坐标或地点网格。
3. 用户聊天内容不自动公开到地图。
4. 用户对模型推荐结果的修改需要记录下来，用于后续训练。
5. 模型预测结果需要记录模型版本，方便回溯和评估。

### 10.1 用户表 users

| 字段              | 类型       | 说明                     |
| --------------- | -------- | ---------------------- |
| id              | bigint   | 用户 ID                  |
| anonymous_id    | varchar  | 匿名标识                   |
| anonymous_token_hash | varchar | 匿名 token 哈希值，不存明文 token |
| nickname        | varchar  | 可选昵称                   |
| user_type       | varchar  | anonymous / registered |
| created_at      | datetime | 创建时间                   |
| last_active_at  | datetime | 最近活跃时间                 |
| status          | varchar  | normal / banned        |

### 10.2 情绪记录表 emotion_posts

| 字段             | 类型       | 说明                                  |
| -------------- | -------- | ----------------------------------- |
| id             | bigint   | 情绪记录 ID                             |
| user_id        | bigint   | 用户 ID                               |
| emotion_type   | varchar  | 情绪类型                                |
| sentiment      | varchar  | 情感倾向，positive / neutral / negative |
| temperature    | int      | 温度值，-10 到 10                        |
| temperature_bin | varchar | 温度区间，very_cold / cold / neutral / warm / hot |
| content        | text     | 一句话内容                               |

## 13. NLP 情感分析与模型训练设计

### 13.1 模块定位

NLP 情感分析模块负责把用户输入的自然语言转化为结构化情绪数据。

它和智能体聊天模块不是同一个东西：

```text
NLP 情感分析模块：负责判断
智能体聊天模块：负责表达
```

例如用户输入：

```text
我今天在图书馆待了一整天，感觉快被 ddl 压垮了。
```

NLP 模块输出：

```json
{
  "emotionType": "stressed",
  "sentiment": "negative",
  "temperature": -6,
  "temperatureBin": "cold",
  "safetyLevel": "normal"
}
```

智能体再基于这个结果生成回应或匿名留言。

### 13.2 处理流程

```text
用户输入一句话
    ↓
文本清洗
    ↓
PaddleNLP 情感分析 / 情绪分类模型
    ↓
输出情绪标签、情感倾向、温度区间、安全等级
    ↓
前端自动填充投递表单
    ↓
用户确认或修改
    ↓
修改结果写回 GaussDB
    ↓
作为下一轮训练数据
```

### 13.3 模型任务拆分

第一版不要把任务设计得过重，建议按阶段实现。

#### 第一阶段：情绪分类

输入用户留言，输出一个情绪标签。

标签建议：

```text
lonely   孤独
anxious  焦虑
stressed 压力
tired    疲惫
sad      失落
calm     平静
healed   治愈
secure   安心
happy    快乐
hopeful  希望
```

#### 第二阶段：情感倾向分析

判断文本整体倾向：

```text
positive / neutral / negative
```

#### 第三阶段：温度预测

MVP 阶段建议先做温度区间分类，而不是直接预测具体温度。

```text
very_cold  -10 到 -7
cold       -6 到 -3
neutral    -2 到 +2
warm       +3 到 +6
hot        +7 到 +10
```

如果后续数据量充足，再训练回归模型预测具体温度值。

#### 第四阶段：风险等级识别

识别高风险内容：

```text
normal  普通情绪表达
warning 明显低落、崩溃、强烈焦虑
crisis  自伤、自杀、伤害他人风险
```

安全等级不能只依赖模型。MVP 阶段建议使用：

```text
关键词规则 + 模型判断 + 后台审核
```

### 13.4 PaddleNLP 方案

推荐使用 PaddleNLP，原因：

1. 中文 NLP 支持较好。
2. 有现成的情感分析能力。
3. 可以基于 ERNIE / BERT 类中文预训练模型微调。
4. 适合课程项目展示模型训练流程。

#### 快速 Demo 方案

MVP 可以先使用 PaddleNLP Taskflow 做情感分析。

```python
from paddlenlp import Taskflow

senta = Taskflow("sentiment_analysis")
result = senta(["我今天真的好累，不知道为什么。"])
print(result)
```

该方案适合快速跑通 Demo，但它主要解决正负向判断，不能完整覆盖本项目的细粒度情绪标签。

#### 正式训练方案

正式版本建议使用 PaddleNLP 微调中文预训练模型：

```text
base_model: ernie-3.0-medium-zh / bert-wwm-chinese / roberta-wwm-ext
task: text classification
input: 用户留言文本
output: emotion_label / sentiment_label / temperature_label
```

模型服务建议单独部署为 FastAPI 服务：

```text
后端业务服务
    ↓ HTTP
NLP Model Service
    ↓
PaddleNLP 模型推理
```

这样可以避免模型推理和业务接口耦合过重。

### 13.5 数据集构建方案

数据集不要依赖单一来源。推荐采用四类数据。

训练数据文件建议使用 JSONL 格式，每行一条样本，便于后续脚本读取和增量追加。

标准字段：

```json
{"text":"ddl 压得我喘不过气。","emotion_label":"stressed","sentiment_label":"negative","temperature_label":"cold","temperature_value":-6,"safety_label":"normal","location_type":"library","source":"mock"}
```

也可以同步导出 CSV，方便人工标注：

```csv
text,emotion_label,sentiment_label,temperature_label,temperature_value,safety_label,location_type,source
ddl 压得我喘不过气。,stressed,negative,cold,-6,normal,library,mock
湖边坐了一会儿，心终于安静下来。,calm,positive,warm,4,normal,lake,mock
```

#### 1. 自建校园情绪数据集

这是最重要的数据来源，因为它最贴近《孤岛温差》的场景。

建议人工编写或整理 800 - 1500 条短文本，每条包含：

```text
text
emotion_label
sentiment_label
temperature_label
temperature_value
safety_label
location_type
```

示例：

```json
{
  "text": "ddl 压得我喘不过气。",
  "emotion_label": "stressed",
  "sentiment_label": "negative",
  "temperature_label": "cold",
  "temperature_value": -6,
  "safety_label": "normal",
  "location_type": "library"
}
```

```json
{
  "text": "湖边坐了一会儿，心终于安静下来。",
  "emotion_label": "calm",
  "sentiment_label": "positive",
  "temperature_label": "warm",
  "temperature_value": 4,
  "safety_label": "normal",
  "location_type": "lake"
}
```

#### 2. PaddleNLP 内置公开数据集

可以使用公开中文情感分析数据集作为辅助训练或预训练验证，例如中文评论情感数据。

注意：

1. 公开数据集通常只有正负向标签。
2. 它们不一定包含校园、地图、地点情绪语境。
3. 不能直接替代本项目自己的细粒度情绪数据集。

#### 3. 用户真实投递数据

用户发布情绪时会主动选择标签和温度，这天然就是弱标注数据。

```text
用户留言 + 用户选择的情绪标签 + 用户选择的温度
```

这些数据可以定期清洗后进入 `nlp_training_samples`。

#### 4. AI 生成样本 + 人工复核

可以让智能体批量生成不同地点、不同情绪、不同温度的训练样本。

但 AI 生成数据必须人工抽查和修正，否则容易出现：

1. 文本模板化。
2. 情绪标签过于理想。
3. 负向样本表达不真实。
4. 风险内容边界不稳定。

### 13.6 微博 API 处理策略

微博 API 不建议作为 MVP 必需依赖，只作为后续可选扩展。

原因：

1. 微博开放接口通常需要开发者账号、应用创建、OAuth 授权和权限审核。
2. 可获取的数据范围和频率受平台策略限制。
3. 微博文本缺少本项目需要的地点温度标签和细粒度情绪标签。
4. 微博语料偏公共舆情，和校园地点情绪存在领域差异。
5. 即使获取到文本，也仍然需要清洗、去重、脱敏和人工标注。

因此文档建议表述为：

```text
微博 API 作为外部公开语料扩展来源，不作为第一阶段必需数据源。
MVP 阶段优先使用自建校园情绪数据集、PaddleNLP 公开数据集和用户投递弱标注数据。
```

如果后续确实使用微博 API，需要增加：

1. OAuth 授权流程。
2. API 调用限流处理。
3. 文本脱敏和去重。
4. 与项目标签体系的重新标注。
5. 数据来源记录字段。

### 13.7 数据标注规范

每条训练样本至少标注：

1. 情绪标签：`emotion_label`
2. 情感倾向：`sentiment_label`
3. 温度区间：`temperature_label`
4. 温度数值：`temperature_value`
5. 安全等级：`safety_label`

标注原则：

1. 先判断具体情绪，再判断正负倾向。
2. 温度体现情绪强度，不只是正负。
3. 同一句话只能有一个主情绪标签。
4. 风险内容优先保证召回，宁可进入人工审核。
5. 用户修正结果优先级高于模型推荐结果。

### 13.8 训练集划分

建议按以下比例划分：

```text
训练集 train：70%
验证集 dev：15%
测试集 test：15%
```

划分时要保证各情绪标签分布尽量均衡，避免模型只会预测高频标签。

### 13.9 评估指标

模型评估不能只看 accuracy。

建议使用：

1. Accuracy：整体分类准确率。
2. Macro-F1：衡量各情绪类别整体效果。
3. Confusion Matrix：查看哪些情绪容易混淆。
4. Temperature MAE：温度预测平均误差。
5. Safety Recall：高风险内容召回率。
6. User Acceptance Rate：用户采纳模型推荐的比例。
7. Correction Rate：用户修改模型推荐的比例。

其中安全等级识别最关注召回率，不能只追求准确率。

### 13.10 训练与部署流程

```text
GaussDB 导出 nlp_training_samples
    ↓
文本清洗与标签检查
    ↓
划分 train / dev / test
    ↓
使用 PaddleNLP 微调模型
    ↓
在 test 集评估
    ↓
记录 nlp_model_versions
    ↓
部署 NLP Model Service
    ↓
业务后端调用 /api/nlp/analyze
    ↓
用户反馈写入 ai_feedback_logs
    ↓
定期重新训练
```

### 13.11 MVP 与进阶边界

MVP 阶段：

1. PaddleNLP Taskflow 或简单分类模型。
2. 自建 300 - 500 条标注样本。
3. 情绪标签推荐。
4. 温度区间规则映射。
5. 高风险关键词规则。

完整版本：

1. 自建 1000 条以上标注样本。
2. 微调 ERNIE / BERT 中文分类模型。
3. 支持情绪分类、情感倾向、温度区间预测。
4. 用户反馈回流训练集。
5. 记录模型版本与评估指标。

后续扩展：

1. 使用微博 API 或公开社交媒体语料增强泛化能力。
2. 使用 embedding 做相似情绪检索。
3. 对地点建立情绪主题聚类。
4. 使用多任务学习同时预测情绪、温度和安全等级。

### 13.12 模型服务兜底策略

NLP 模型服务不能成为情绪投递流程的单点故障。

当 PaddleNLP 服务不可用、响应超时或置信度过低时，系统回退到规则策略：

```text
关键词词典
    ↓
情绪标签默认映射
    ↓
强度词修正温度
    ↓
高风险关键词兜底检测
```

示例：

| 关键词              | 推荐情绪 | 默认温度 |
| ----------------- | ------ | ------ |
| ddl、考试、复习、压垮 | 压力   | -5℃    |
| 好累、撑不住、疲惫     | 疲惫   | -4℃    |
| 一个人、没人懂、空荡    | 孤独   | -5℃    |
| 安静、舒服、平静       | 平静   | +2℃    |
| 治愈、被接住、安心      | 治愈   | +5℃    |

强度修正：

```text
“有点”  温度绝对值降低 1
“很 / 真的”  温度绝对值增加 1
“快崩溃 / 撑不住”  温度降低到 -7℃ 以下，并触发 warning 检查
```

兜底结果需要标记：

```text
model_version = rule_fallback_v1
confidence = 0.50
```

## 14. 内容安全与隐私设计

### 14.1 隐私保护

1. 默认匿名。
2. 不展示真实身份。
3. 不展示精确用户 ID。
4. 不展示精确行动轨迹。
5. 坐标模糊化处理。
6. 用户可以删除自己的内容。
7. 不读取通讯录、相册、聊天记录等敏感数据。
8. 聊天内容不自动发布到地图。
9. 用户确认后，智能体生成的内容才可作为情绪投递。
10. anonymousToken 只在客户端保存，服务端只保存 token hash。
11. 进入训练集的数据必须先脱敏，移除姓名、电话、学号、宿舍号等个人信息。
12. 高风险聊天内容不进入公开地图展示。

### 14.2 聊天内容与训练数据边界

聊天内容和公开投递内容需要分开处理：

1. 用户与智能体的原始聊天内容默认只用于当前会话展示和安全判断。
2. 聊天内容不会自动发布到地图。
3. 只有用户点击“使用这条留言”并确认发布后，生成内容才会进入 emotion_posts。
4. 原始聊天内容如需进入训练集，必须先做脱敏处理。
5. safetyLevel = crisis 的聊天内容不进入训练集自动样本池，只进入安全预警和人工审核流程。
6. 用户删除会话后，前端不可再展示该会话，后端按数据保留策略标记 deleted。

### 14.3 坐标模糊化

用户真实坐标：

```text
latitude = 39.123456
longitude = 116.123456
```

存储时可以处理为：

```text
latitude = 39.123
longitude = 116.123
```

或者随机偏移 100 - 300 米。

MVP 阶段建议直接四舍五入到三位小数，并生成 location_grid。

位置展示规则：

1. 不保存原始精准坐标。
2. 地图前端展示模糊坐标或地点中心点。
3. 低密度区域不展示单个真实点，只展示聚合结果。
4. 同一 location_grid 内公开情绪数量少于 3 条时，不生成公开统计。
5. 后台可以查看模糊坐标，但不提供用户行动轨迹。

### 14.4 内容审核

需要处理：

1. 辱骂攻击
2. 色情内容
3. 广告
4. 人身威胁
5. 自伤自杀风险内容
6. 个人隐私泄露
7. 引战和恶意内容

### 14.5 智能体安全分级

| 等级      | 类型           | 处理方式              |
| ------- | ------------ | ----------------- |
| normal  | 普通情绪表达       | 正常回应              |
| warning | 明显低落、焦虑、崩溃   | 温和安抚，引导求助         |
| crisis  | 自伤、自杀、伤害他人风险 | 显示紧急求助提示，建议联系现实支持 |

发布规则：

1. normal 内容可以正常发布。
2. warning 内容可以发布，但需要经过敏感词和隐私检测。
3. crisis 内容不直接公开展示，进入后台审核队列。
4. crisis 内容发布时，前端优先显示求助提示，而不是鼓励用户继续投递。
5. 管理员审核通过前，crisis 内容不参与公开热力图和统计报告。

### 14.6 高风险内容处理文案

如果检测到严重负面内容，可以显示：

```text
如果你现在非常难受，请先联系身边可信任的人，或寻求学校心理咨询中心、当地心理援助机构、急救服务的帮助。

你不需要一个人撑过这一刻。
```

## 20. 答辩展示方案

### 20.1 推荐演示流程

1. 打开首页，展示校园温差地图。
2. 切换不同情绪图层，例如孤独、焦虑、治愈。
3. 点击图书馆，展示地点情绪档案。
4. 浏览匿名故事墙。
5. 打开智能体“岛屿回声”。
6. 输入：“我今天在图书馆待了一天，感觉很累。”
7. 展示 NLP 情感分析结果：疲惫 / negative / -4℃。
8. 智能体基于分析结果生成一句话留言。
9. 点击“使用这条留言”。
10. 跳转情绪投递页并自动填充。
11. 用户点击发布。
12. 地图上出现新的情绪点。
13. 点击共鸣按钮。
14. 展示今日温差报告。
15. 展示后台审核功能。
16. 展示 GaussDB 中的情绪记录、预测记录和反馈记录。
17. 说明隐私保护、数据安全和模型训练闭环。

### 20.2 答辩亮点表达

可以这样介绍：

```text
传统地图告诉我们一个地方在哪里，而《孤岛温差》尝试回答另一个问题：一个地方曾经承载过怎样的情绪。

我们希望通过匿名情绪投递、温差地图和智能体陪伴，让城市中看不见的孤独、压力、治愈和共鸣被温柔地看见。
```

智能体部分可以这样介绍：

```text
我们加入了一个情绪陪伴智能体“岛屿回声”。它不是传统客服，也不是心理医生，而是一个帮助用户整理情绪、生成匿名留言、理解地点温度的陪伴入口。

用户有时候并不知道如何表达自己的情绪，所以智能体可以先接住用户的一句话，再帮助用户转化成情绪标签、温度值和地图留言。这样，AI 功能不是孤立存在的，而是和情绪地图、地点档案、温差报告形成完整闭环。
```

NLP 与模型训练部分可以这样介绍：

```text
我们没有只把 AI 当成聊天功能，而是单独设计了 NLP 情感分析模块。用户输入一句话后，系统会通过 PaddleNLP 模型识别情绪类型、情感倾向、温度区间和安全等级。

这些预测结果会写入 GaussDB。如果用户修改了模型推荐的情绪或温度，修改结果也会被记录为反馈数据，用于后续重新训练模型。这样系统形成了“用户表达 - 模型分析 - 用户修正 - 数据回流 - 模型迭代”的闭环。
```

GaussDB 部分可以这样介绍：

```text
本项目使用 GaussDB 作为统一数据底座，不只存储用户、情绪记录和互动数据，也存储 NLP 训练样本、模型版本、预测结果和用户反馈。这样业务系统和模型训练流程可以围绕同一套数据资产展开。
```

## 21. 项目风险与解决方案

### 21.1 初期数据不足

问题：

没有足够用户投稿，热力图不好看。

解决方案：

1. 使用模拟数据。
2. 先做校园场景。
3. 准备 300 条以上种子数据。
4. Demo 时演示实时投稿后地图变化。
5. 额外准备 300 - 500 条 NLP 标注样本。

### 21.2 隐私风险

问题：

情绪和位置数据较敏感。

解决方案：

1. 匿名发布。
2. 坐标模糊化。
3. 不展示用户轨迹。
4. 用户可删除内容。
5. 不读取通讯录、相册等敏感权限。
6. 聊天内容不自动公开。
7. NLP 训练样本进入训练集前先脱敏。

### 21.3 内容安全风险

问题：

用户可能发布攻击性、广告或极端负面内容。

解决方案：

1. 敏感词过滤。
2. 举报机制。
3. 后台审核。
4. 高危内容提示文案。
5. 严重违规内容隐藏。
6. 高风险样本优先进入人工审核。

### 21.4 智能体风险

问题：

智能体可能被用户误认为专业心理咨询。

解决方案：

1. 明确智能体定位是情绪陪伴，不是心理诊断。
2. 高风险内容触发求助提示。
3. 不使用绝对化承诺。
4. 不鼓励用户依赖智能体。
5. 不自动保存或公开敏感聊天内容。

### 21.5 NLP 模型效果风险

问题：

初期训练数据较少，模型可能出现情绪分类不准、温度推荐偏差、安全风险漏判等问题。

解决方案：

1. MVP 阶段先使用规则 + PaddleNLP Taskflow 或简单分类模型。
2. 情绪标签数量控制在 8 - 10 个。
3. 温度预测先做区间分类，不直接做复杂回归。
4. 用户可以手动修改模型推荐结果。
5. 用户修正结果写入反馈表，用于后续训练。
6. 高风险内容使用关键词规则和人工审核兜底。

### 21.6 微博 API 依赖风险

问题：

微博 API 需要账号、应用审核、OAuth 授权和接口权限，不适合作为 MVP 的核心依赖。

解决方案：

1. MVP 不依赖微博 API。
2. 第一阶段使用自建校园情绪数据集。
3. 使用用户投递数据作为弱标注数据。
4. 微博 API 只作为后续公开语料扩展来源。
5. 如果接入微博 API，需要增加脱敏、去重、限流和重新标注流程。

### 21.7 GaussDB 适配风险

问题：

GaussDB 与 MySQL / PostgreSQL 在 SQL 方言、驱动、扩展能力和云环境配置上可能存在差异。

解决方案：

1. 尽量使用标准 SQL 和 ORM。
2. MVP 阶段不强依赖复杂 GIS 扩展。
3. 经纬度查询先用普通字段 + 后端距离计算实现。
4. 向量检索、GIS 空间索引作为后续增强。
5. 提前准备数据库初始化脚本和连接配置说明。

### 21.8 功能范围过大

问题：

项目容易失控。

解决方案：

第一版只做：

1. 地图
2. 情绪投递
3. 热力图
4. 故事墙
5. 共鸣互动
6. 智能体基础聊天
7. 统计报告
8. 基础后台
9. GaussDB 存储
10. NLP 情感分析基础接口

复杂推荐、多城市运营、语音聊天、长期 AI 记忆、微博 API 自动采集、大规模多任务训练放到后续版本。

## 22. GaussDB 初始化 SQL 草案

以下 SQL 为核心表草案，具体字段类型可根据实际 GaussDB 版本和 ORM 规范微调。

### 22.1 用户表

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    anonymous_id VARCHAR(64) NOT NULL UNIQUE,
    anonymous_token_hash VARCHAR(128) NOT NULL,
    nickname VARCHAR(64),
    user_type VARCHAR(32) NOT NULL DEFAULT 'anonymous',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_active_at TIMESTAMP,
    status VARCHAR(32) NOT NULL DEFAULT 'normal'
);
```

### 22.2 情绪记录表

```sql
CREATE TABLE emotion_posts (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    emotion_type VARCHAR(32) NOT NULL,
    sentiment VARCHAR(32),
    temperature INT NOT NULL,
    temperature_bin VARCHAR(32),
    content TEXT NOT NULL,
    latitude DECIMAL(10, 6),
    longitude DECIMAL(10, 6),
    location_grid VARCHAR(64),
    location_name VARCHAR(128),
    visibility VARCHAR(32) NOT NULL DEFAULT 'public',
    allow_reaction BOOLEAN NOT NULL DEFAULT TRUE,
    model_version VARCHAR(64),
    confidence DECIMAL(5, 4),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP,
    status VARCHAR(32) NOT NULL DEFAULT 'normal',
    report_count INT NOT NULL DEFAULT 0,
    CONSTRAINT ck_emotion_temperature CHECK (temperature >= -10 AND temperature <= 10)
);

CREATE INDEX idx_emotion_posts_user_id ON emotion_posts(user_id);
CREATE INDEX idx_emotion_posts_location_grid ON emotion_posts(location_grid);
CREATE INDEX idx_emotion_posts_created_at ON emotion_posts(created_at);
CREATE INDEX idx_emotion_posts_emotion_type ON emotion_posts(emotion_type);
```

### 22.3 互动表

```sql
CREATE TABLE reactions (
    id BIGSERIAL PRIMARY KEY,
    post_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    reaction_type VARCHAR(32) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_reaction_once UNIQUE (user_id, post_id, reaction_type)
);

CREATE INDEX idx_reactions_post_id ON reactions(post_id);
```

### 22.4 NLP 训练样本表

```sql
CREATE TABLE nlp_training_samples (
    id BIGSERIAL PRIMARY KEY,
    text TEXT NOT NULL,
    cleaned_text TEXT,
    sentiment_label VARCHAR(32),
    emotion_label VARCHAR(32),
    temperature_label VARCHAR(32),
    temperature_value INT,
    safety_label VARCHAR(32) NOT NULL DEFAULT 'normal',
    source VARCHAR(32) NOT NULL,
    label_source VARCHAR(32) NOT NULL,
    split VARCHAR(16),
    status VARCHAR(32) NOT NULL DEFAULT 'active',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP,
    CONSTRAINT ck_sample_temperature CHECK (temperature_value IS NULL OR (temperature_value >= -10 AND temperature_value <= 10))
);

CREATE INDEX idx_training_samples_emotion ON nlp_training_samples(emotion_label);
CREATE INDEX idx_training_samples_split ON nlp_training_samples(split);
```

### 22.5 NLP 模型版本表

```sql
CREATE TABLE nlp_model_versions (
    id BIGSERIAL PRIMARY KEY,
    model_name VARCHAR(64) NOT NULL,
    base_model VARCHAR(128),
    train_data_size INT,
    dev_data_size INT,
    test_data_size INT,
    accuracy DECIMAL(6, 4),
    macro_f1 DECIMAL(6, 4),
    temperature_mae DECIMAL(6, 4),
    safety_recall DECIMAL(6, 4),
    model_path VARCHAR(256),
    status VARCHAR(32) NOT NULL DEFAULT 'training',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### 22.6 NLP 预测与反馈表

```sql
CREATE TABLE nlp_predictions (
    id BIGSERIAL PRIMARY KEY,
    target_type VARCHAR(32),
    target_id BIGINT,
    model_version VARCHAR(64) NOT NULL,
    input_text TEXT NOT NULL,
    sentiment_prediction VARCHAR(32),
    emotion_prediction VARCHAR(32),
    temperature_prediction INT,
    safety_prediction VARCHAR(32),
    confidence DECIMAL(5, 4),
    user_corrected BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE ai_feedback_logs (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    prediction_id BIGINT NOT NULL,
    original_emotion VARCHAR(32),
    corrected_emotion VARCHAR(32),
    original_temperature INT,
    corrected_temperature INT,
    accepted BOOLEAN NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_nlp_predictions_target ON nlp_predictions(target_type, target_id);
CREATE INDEX idx_ai_feedback_prediction ON ai_feedback_logs(prediction_id);
```

## 25. 项目总结

《孤岛温差》的核心不是简单地“记录情绪”，而是“让情绪在空间中被看见”。

它把城市或校园变成一张有温度的地图：

有些地方很冷，因为那里承载了很多孤独、焦虑和压力。

有些地方很暖，因为那里留下了很多治愈、安心和希望。

用户不需要暴露身份，也能知道有人和自己有过类似感受。

智能体“岛屿回声”则让用户在还说不清楚自己情绪的时候，先获得一个温柔的表达入口。

因此，《孤岛温差》的完整产品闭环是：

```text
产生情绪
    ↓
和智能体聊聊
    ↓
整理情绪标签与温度
    ↓
匿名投递到地图
    ↓
被他人看见和共鸣
    ↓
发现自己并不是一座真正孤岛
```

《孤岛温差》是一款有明确技术实现路径，也有情感表达和思想气质的软件工程作品。
